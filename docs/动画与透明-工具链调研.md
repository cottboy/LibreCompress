# 动画与透明背景：工具链调研记录

调研日期：2026-10-17
调研目的：在"一种格式一个专精工具、不用 libvips / ImageMagick 这类聚合引擎"的前提下，查清动画与透明背景到底卡在哪里，以及现有工具选择是否合理。

## 证据等级说明

- **【本机实测】**：在当前开发机上跑官方二进制得到的输出。
- **【外部实测】**：外部研究员用官方二进制真实跑出的输出（含体积、误差、退出码数据）。
- **【文档原文】**：官方文档、源码或 `-h` 输出的原文。

凡本机无法复现的结论，均在文中标明来源，不做二次断言。

## 修订记录（2026-10-18）

这份文档写于 2026-10-17，其中"动画 WebP 同格式压缩"的结论**已被后续实测推翻**，正文保留原样作为过程记录，实际实现以本节为准。

- **原结论**：webpmux 抽出每帧压缩码流 → cwebp 逐帧重压 → webpmux 按原参数装回去，是动画 WebP 的最优解。
- **推翻原因（本机实测，webpmux 1.6.0 + ffmpeg 9.0.2）**：
  1. **帧数受命令行长度限制**。`webpmux -frame` 每帧都进命令行，Windows 上限 32767 字符，约 400 帧就爆；而且 N 帧要起 2N 个进程。`webpmux` 虽然有"参数文件"模式可以绕开长度限制，但 **Windows 版被禁用**，报错原文 `Reading arguments from a file is a feature unavailable with Unicode binaries.`
  2. **画布会被裁小**。webpmux 用"所有帧包围盒的并集"当画布，实测 200×150 的留白动图重组后变 170×130。
  3. **`webpmux -duration` 也会重算画布**，所以旧代码里"末帧时长校正"这一步对留白动图同样会裁画布（同一个坑）。
- **新做法**：改用 FFmpeg 的 `libwebp_anim` 一条命令整只重压。实测同一张留白动图：画布 200×150 保住，帧尺寸 20×20 与偏移 10,10 / 80,40 / 150,110 全部保留，循环次数与透明不变；6 帧带透明的素材 q75 从 9272 B 压到 2822 B，逐帧时长 50/100/200/300/150/150 全部一致。
- **新做法的代价**：FFmpeg 的 WebP 编码器没有 `-exact`、也没有 `-alpha_q`（libwebp 默认 alpha 就是无损，影响很小），并且解码出 RGB 再转回 YUV，比 cwebp 的纯 YUV 重压多一代颜色转换——实测同图同 q75 体积反而略小（2564 B vs 2600 B）。
- **实现细节**：`libwebp_anim` 用平均帧时长推算末帧时长（原 150 ms 会变 160 ms），背景色一律写成不透明白，这两处写回后用 `webpmux -duration` / `-set bgcolor` 按原图改回来；`-duration` 只在"帧能盖满画布"时才执行，否则宁可差几毫秒也不裁画布。
- **动画 AVIF 维持 ffmpeg + ffprobe + avifdec**，且 ffprobe 不可省：`direct-varied.avif` 实测有 4 条轨道（0/1 = 封面图，2/3 = 动画的颜色与透明），不按 `nb_frames` 与分辨率挑轨道就会压到封面，动图变静图。avifenc 1.4.2 确实支持多张图当帧（`--timescale` / `--duration` / `--repetition-count`，实测 6 帧、逐帧时长、无限循环全对），但仍需先拆帧，且命令行同样随帧数增长。

## 一、总结论

1. **WebP、GIF、PNG、APNG、JPEG 这五族可以彻底甩掉 ImageMagick 和 FFmpeg。** AVIF 要自己拆帧也能甩掉；JPEG XL 最省事，官方工具天生就吃 GIF / APNG 动画。
2. **"为了透明背景牺牲太多"这个感觉是错的。** 静态透明图完全靠专精工具就能做，成本接近于零；真正的成本中心是**动画的跨格式转换**，而不是透明。
3. ~~**当前最亏的一处是动画 WebP 同格式压缩。** 走 ImageMagick 的 `-coalesce` 路线，实测结果比原图**大 29%**，且画面画错（最大像素差 255）；换成 libwebp 自带工具的原样重组路线，体积更小、元数据全保。~~ → 已被 2026-10-18 修订推翻：改用 FFmpeg `libwebp_anim` 一条命令，见《修订记录》。
4. 业界没有任何项目做到"纯本地 + 零聚合引擎 + 全动画格式互转"，但最小可行组合是成熟的：**libwebp + gifsicle + apng 家族 + oxipng + avifenc + libjxl**。

## 三、当前各格式工具使用审计

| 格式 | 现在用的工具 | 是否合理 | 说明与建议 |
| --- | --- | --- | --- |
| JPEG 同格式 | jpegoptim | 合理 | 只做无损优化，安全。但它**改不了色度抽样**，想要更小必须另开有损重编码通道 |
| JPEG CMYK→RGB | ffmpeg + GD | **不合理** | 换成 `djpeg` + `cjpeg`：更准、更小、少一个聚合引擎，还能顺手甩掉 GD |
| PNG 有损 | pngquant | 合理 | 唯一选择。已正确处理 rc=98 / 99。但**版本落后**，且 `--quality=min-max` 的窄区间在纯渐变图上容易触发 rc=99 不输出 |
| PNG 无损 | oxipng | 合理 | 唯一还在活跃维护的。代码已用 `--strip=safe`，避开了会毁 APNG 的 `all`，正确 |
| WebP 静态 | cwebp | 合理 | 未显式设 `-alpha_q`，走默认 100，正确。可增加 `-preset icon`（UI/logo 类）与 `-alpha_filter best` |
| WebP 动画 | **ImageMagick** → **ffmpeg (libwebp_anim)** | 已改 | 见《修订记录》：webpmux 逐帧重组受命令行长度与画布裁切限制，已换成 FFmpeg 一条命令 |
| WebP 动图转换 | gif2webp | 合理 | GIF→WebP 一条命令即可，本来就不需要 FFmpeg。但**有损时缺 `-exact`** |
| AVIF 静态 | avifenc + avifdec | 合理 | 未设 `--qalpha`，走默认值；带 alpha 的图走 4:2:0 会明显劣化半透明边缘 |
| AVIF 动画 | **ffmpeg** | 可用但非最优 | avifenc 1.4.2 本身支持多帧编码，只差自己拆帧 |
| AVIF 信息读取 | **ffprobe** | **不合理** | `avifdec --info` 已给出全部所需字段 |
| GIF | gifsicle | 最优 | 同格式压缩与帧信息读取都靠它，无可替代 |
| APNG 同格式 | oxipng | 合理 | 唯一活跃方案 |
| APNG → WebP | **ffmpeg** | 现实妥协 | 这是全项目**唯一真正补不上的洞**，见第四节 |
| APNG / GIF → JXL | cjxl | 最优 | cjxl 原生读 GIF / APNG，连子矩形 delta 帧都保留 |
| SVG | svgo | 合理 | 依赖 Node 运行时，若想纯二进制可考虑 oxvg |

## 四、去掉聚合引擎的替换方案

### 4.1 ImageMagick（动画 WebP 重压）→ libwebp 自带工具【外部实测】

```bat
webpmux -info in.webp                              :: 读全部逐帧字段
webpmux -get frame 1 in.webp -o f1.webp            :: 抽压缩码流（不解码像素）
cwebp -q 55 -m 6 -alpha_q 80 f1.webp -o r1.webp    :: 重压这一帧
webpmux -frame r1.webp +120+0+0+0+b -frame r2.webp +80+2+2+1+b ^
        -frame r3.webp +60+6+6+0-b -loop 5 -bgcolor 12,34,56,78 -o out.webp
webpmux -set icc p.icc out.webp -o o1.webp         :: ICC/EXIF/XMP 必须链式一条条补
webpmux -set exif e.exif o1.webp -o final.webp
anim_diff in.webp final.webp                       :: 免费回归校验
```

关键事实：

- `webpmux -get frame n` 抽出的是**压缩位流**（VP8 / VP8L），不是像素。抽出的文件就是标准的非动画 WebP 单帧文件，能直接喂 cwebp。【文档原文 + 外部实测】
- `dwebp` **不支持**逐帧解码，官方文档原文写着 `Animated WebP files are not supported`。【文档原文 + 外部实测】
- 真正能"逐帧解码成整画布像素"的只有 `anim_dump`，它会按 dispose / blend 语义做完整合成。但它是半官方工具。【文档原文】
- `duration / x,y 偏移 / dispose / blend / loop / bgcolor / ICC` 都能从 `webpmux -info` 读回并原样写回。

### 4.2 FFmpeg（CMYK JPEG → RGB）→ djpeg + cjpeg【外部实测】

```bat
djpeg.exe -pnm in.jpg | cjpeg.exe -quality 85 -optimize -progressive -outfile out.jpg
djpeg.exe -png -outfile tmp.png in.jpg
cjpeg.exe -quality 85 -optimize -progressive -outfile out.jpg tmp.png
```

- 版本要求：CMYK→RGB 是 **libjpeg-turbo 3.1.0** 才加上去的；要 `djpeg -png` 输出需 **≥ 3.2.0**。
- CMYK→RGB 是**无文档行为**，源码注释自称 `quick & dirty`、`suitable for testing purposes only`，但实测比现在走 FFmpeg 更准。
- 色彩正确性实测（同一张 800×600 图，基准为转 CMYK 前的原图）：

| 路径 | MAE | PSNR |
| --- | --- | --- |
| djpeg -pnm（CMYK 输入） | 2.383 | 38.44 |
| ffmpeg 解同一文件（现方案） | 2.521 | 37.99 |
| djpeg -pnm（YCCK 输入） | 3.828 | 34.10 |

- 体积：djpeg + cjpeg q85 = 79,205 B；ffmpeg→PNG→GD q85 = 91,091 B，**小 13%**。
- `jpegtran` 做不了 CMYK→RGB（它是 DCT 域无损工具），`cjpeg` 也没有色彩空间转换开关。
- 反相 CMYK：库**不会**替你修正 Photoshop 写的反相数据，只能靠 `djpeg -verbose` 打出的 `Adobe APP14 marker ... transform 0/2` 自己判断。
- 默认 4:2:0 会压烂小色块：实测小色块图最大通道差 141，加 `-sample 1x1,1x1,1x1` 降到 38。**文字 / logo 必须 4:4:4。**

### 4.3 ffprobe（读动画 AVIF 信息）→ avifdec / 纯盒子解析【外部实测】

- `avifdec --info` 直接给出：帧数、timescale、每帧时长、循环次数、alpha 是否预乘、位深、色彩、ICC / Exif / XMP 是否存在。缺点是要真解码，慢。
- 逐帧解码用 `--index N` 或 `--index all`（**没有** `--frame` 参数）。
- 纯解析路线：动画 AVIF 的帧数在 `stsz.sample_count`、每帧时长在 `stts`、timescale 在 `mdhd`、循环在 `edts/elst`，alpha 是第二条 `auxv` 轨道。**不是** `iinf/iloc`，也没有 `moof/mfra` 分片结构。
- 现成解析器：Bento4 的 `mp4info` / `mp4dump` 最适合脚本。exiftool 读不出帧数，MediaInfo 会把 alpha 轨道算成帧数，都不要用。

### 4.4 FFmpeg（APNG → 动画 WebP）：唯一真缺口

- `gif2webp` **读不了 APNG**（它静态链接 giflib，物理上不可能解析 PNG 容器）。三重证据：文档原文、源码 `#include <gif_lib.h>`、实测报 `GIFLib Error 103`。
- `img2webp` 的 WIC 入口**做不到**：源码 `wicdec.c` 里 `frame_count > 1` 直接 `E_FAIL`，且**不打印任何错误**；这是 2020 年的一个专门提交，属刻意设计。而且 WIC 根本没有 APNG 解码器。
- 可行的替代是 `apngdis`（抽出子矩形帧 + 全字段 fcTL 的 JSON）→ 自己合成满画布 → `img2webp`。但 `apngasm` 拒绝 apngdis 的输出（`different image size`），中间的合成必须自己做。**这跟插件"不拆帧、不在 PHP 里做像素运算"的原则冲突，风险高。**

### 4.5 FFmpeg（动画 AVIF）：可换成 avifenc 多帧

- avifenc **1.4.2 本身支持多帧**：`--duration`、`--timescale`、`--repetition-count`。但它只认 AVIF / JPEG / PNG / Y4M 输入，**读不了 GIF**。
- 一条命令替代方案：`avif-go` 的 `avif encode anim.gif out.avif`，内置 GIF 合成逻辑，延时与循环次数保真。但它参数极少、未签名、读不了 WebP。
- 坑：avifenc 喂 APNG 会**静默只出第一帧**并返回成功。
- 坑：`-d` 是 depth 不是 duration，网上大量老教程已失效。
- 坑：动画序列里只有第一帧的 ICC / Exif / XMP 会被保留。

## 五、动画 WebP 重压：三条路线对比【外部实测】

测试对象：826 B 的动画 WebP。

| 方案 | 结果 |
| --- | --- |
| A：抽码流 → cwebp → webpmux 原样重组（2026-10-18 已废弃，见《修订记录》） | 820 B，元数据全保；纯 re-mux 时与原文件逐字节相同 |
| B：anim_dump 全画布 → cwebp → webpmux（≈ 现在的 ImageMagick 路线） | **1062 B，反而大 29%**，bgcolor / loop / dispose 被抹平，anim_diff 报最大像素差 255 |
| C：anim_dump → img2webp -min_size | 882 B，img2webp 会自己重算帧间差分 |

**结论：选 A，别用 B。** 现在代码里 `class-animation.php` 的 `magick ... -coalesce` 正是 B 的做法。

### 该路线的坑

- **画布尺寸不可指定**：`webpmux` 从帧包围盒推导画布尺寸，原文件 100x80 会被裁成 70x60。首帧是小 delta 帧时损失不可逆。
- **奇数偏移会被静默改成偶数**：`Warning: odd offsets will be snapped to even values`。
- **`-frame` 重组会清零元数据**：bgcolor 回 `0xFFFFFFFF`、loop 回 0、ICC / EXIF / XMP 全丢，必须链式 `-set` 补回。
- **一次调用只能一个 `-set`**：多个会报 `Multiple '-set' arguments specified`。
- `-duration` 与 `-frame` 互斥，但 `-duration` 是唯一"不重压像素只改时间"的原地编辑。
- 只有一帧时 `-frame` 会输出非动画文件，`-loop` / `-bgcolor` 被静默忽略。

## 六、透明与画质调参【外部实测】

### WebP

- `-alpha_q` 默认 **100**（无损）。**反直觉**：降到 90 / 80 文件反而变大 6~8%，要省就得一步跳到 ≤60。

| alpha_q | 字节 | 最大 alpha 误差 | 被硬推到 0/255 的边像素 |
| --- | --- | --- | --- |
| 100 | 8052 | 0 | 0 |
| 80 | 8736 | 2 | 48 |
| 60 | 6972 | 10 | 440 |
| 0 | 5694 | 127 | 5928（全毁） |

- `-exact` **静态图别加**（有损模式加它纯付 16% 体积税）；**动画必须加**——官方 `img2webp -h` 原文写着默认值 `may cause artifacts with lossy animations`。
- 半透明边缘发暗的根因不是 `-exact`，而是 alpha 全分辨率无损、RGB 色度 4:2:0 半分辨率有损，两者在斜边上必然错位（峰值边误差约 19/255）。
- `-alpha_method` 默认是 **1**（不是 4）；`-alpha_method 0` 体积会涨到 11.8 倍。
- 坑：cwebp 自带的 `-print_psnr` / `-print_ssim` **完全不看 alpha**，透明图的质量验收必须解码后逐像素比。

### AVIF

| 参数 | 字节 | 环带平均误差 | 最大误差 | 误差 >8 的像素 |
| --- | --- | --- | --- | --- |
| 涂主体色，默认 | 8772 | 0.33 | 5.6 | 0 |
| `-p` 预乘 | 7090（−19%） | 1.00 | 17.7 | 21 |
| `-y 420 --sharpyuv` | 8334 | 0.62 | 22.7 | 81 |
| `-r limited` | 7916 | 0.72 | 19.1 | 137 |

- `--qalpha`：100 无误差；**90 是甜点**（−27%，最大误差仅 7）；80 再小一点但误差开始涨。
- `-p` 预乘省 19%，但边缘误差翻 3 倍，且让"透明区涂黑 / 涂主体色"的优化空间彻底消失。
- `-r limited` 是实测里最严重的描边劣化源。
- alpha 是独立的单色 aux 图，**不受 4:2:0 影响**。

### PNG / pngquant

- 色带的根因：pngquant 把 RGBA 塞进最多 256 条共享调色板，**alpha 级数和颜色数是同一份预算**，砍色数就是砍 alpha 台阶。

| 参数 | 字节 | 剩余 alpha 级数 | 相邻 alpha 最大跳变 |
| --- | --- | --- | --- |
| 默认 256 色 | 44,219 | 157 | 9 |
| 64 色 | 33,827 | 56 | 17 |
| `--posterize 4` | 55,578 | 19 | 17 |

- 治法：保持 256 色 + 默认 `--floyd=1`；要更好画质用 `--speed 1`；**别用 `--posterize`**。
- 必须处理的退出码：质量不达标 rc=99、`--skip-if-larger` rc=98（**代码已处理**）。
- 何时换格式：色带 + 平滑 alpha + 颜色少 = PNG 调色板已到极限 → 改 `-near_lossless 60` 或 WebP 无损；照片类透明图直接走 WebP / AVIF 有损。

### APNG 的炸弹

- `oxipng --strip all` **会把 APNG 转成普通 PNG**（官方 `--help` 原文警告）。实测报告"省 99.05%"，但 acTL / fcTL / fdAT 全没了，动画彻底消失。
- **永远只用 `--strip safe`**（代码已正确使用）。
- `apngopt` 是唯一能做帧间差分重算的工具，但 2015 年停更、官方只剩 GUI exe，无头服务器用不了。
- `zopflipng` 会把 APNG 拍成单帧，不要用。

## 七、参数名纠错表

网上流传的不少参数并不存在，照抄会直接报错：

| 错误写法 | 正确写法 |
| --- | --- |
| `oxipng --frames` | 不存在，oxipng 只能整只优化 APNG |
| `img2webp -time` | `-d`（逐帧时长，写在每个帧文件名前） |
| `avifenc --loop` | `--repetition-count` |
| `avifenc --matrix` | `--cicp` / `--nclx` 的第三个数 |
| `avifenc --quality-alpha` / `--alpha-method` | `--qalpha` |
| `avifenc -d 100`（当 duration 用） | `-d` 是 depth；`--duration` 无短选项 |
| `pngquant --dithering` | `--floyd[=N]`，默认 1 |
| `cwebp -alpha_method 4` | 默认 1，`-m` 才是 compression method |
| `gif2webp` 读 APNG | 读不了，只认 GIF |
| `apngsplit` | 未查到实体 |
| `cavif` 支持动画 | 不支持 |

另外：`avifenc` 第一帧的 duration 会继承命令行最后一个 `--duration`，必须在第 0 帧前也写一次。

## 八、权衡结论：动画、透明与"体积小画质好"的关系

核心判断：**这三件事不是同一个开关，别用"放弃动画和透明"去换画质。**

### 8.1 透明几乎不吃成本

静态透明图全部由专精工具搞定：`cwebp -alpha_q`、`avifenc --qalpha`、`oxipng`、`pngquant`。**一个聚合引擎都不需要。** 放弃透明换不到任何工具链简化。

透明真正付出的代价只有两处，而且都是参数选择，不是能力缺失：

1. AVIF 默认开 4:2:0 会让半透明边缘最大误差从 5.6 涨到 22.7。**带 alpha 的图应该走 `-y 444`**，代价只是体积稍大。
2. 留在 PNG 调色板里的平滑 alpha 必然色带，该走 WebP / AVIF 有损。

### 8.2 动画才是成本中心，但可以砍到接近零

| 用途 | 现状 | 换掉之后 |
| --- | --- | --- |
| 动画 WebP 重压 | ImageMagick → ffmpeg (libwebp_anim) | 已改，**净赚**（不限帧数、画布不缩水、一条命令） |
| CMYK JPEG → RGB | ffmpeg + GD | djpeg + cjpeg，**净赚**（更准、小 13%、少两个组件） |
| 读动画 AVIF 信息 | ffprobe | avifdec --info 或纯盒子解析，**净赚** |
| APNG → 动画 WebP | ffmpeg | 无等价替代，保留 |
| 动画 AVIF 输出 | ffmpeg | avifenc 多帧或 avif-go，需自己拆帧 |

**建议把动画拆成两条通道：**

1. **无损通道（默认开，零聚合引擎）**：`gifsicle`、`oxipng --strip safe`、`cjxl` 原生读 GIF / APNG。这条通道不需要 ImageMagick；动画 WebP 重压除外，它现在固定走 FFmpeg。
2. **跨格式转换通道（默认关，用户可选）**：APNG → WebP / AVIF、动画有损重压。开启时才需要 FFmpeg 或 avif-go。

这样默认安装的插件**既支持动图又零聚合引擎**，需要转换的用户再单独开。

### 8.3 "压缩率高一点、质量好一点"的真正杠杆（按收益排序）

1. **JPEG 有损重编码开关**：现在 jpegoptim 只能无损优化、改不了抽样。加一条可选的 `cjpeg`（或 mozjpeg）路径 `-quality 82 -optimize -progressive`，文字 / logo 类再加 `-sample 1x1`。这是最大的单点收益，且完全不碰动画。
2. **AVIF 带 alpha 时走 `-y 444` + 显式 `--qalpha 90`**（现在没设 qalpha，走的是默认值）。
3. **WebP 有损动图加 `-exact`**（Google 自己承认默认会出伪影）；静态 UI / logo 加 `-preset icon`。
4. **pngquant 升到 3.0.3**（现在是 2021 年的 2.17.0），并收紧 `--quality` 区间策略避免渐变图频繁不输出。
5. **按图内容自动选格式**（照片 → AVIF，UI / logo → WebP near-lossless 或 PNG）——比任何单点参数都管用。

### 8.4 "WordPress 也用 ImageMagick，我再用就鸡肋"——这个担心可以放下

WordPress 核心的 Imagick 编辑器本质上只做**改形状 + 出子尺寸**：resize / crop / rotate / thumbnail / multi_resize。它传给编码器的全部旋钮只有两个：WebP 的 `lossless` 和 AVIF 写死的 `heic:speed=7`。**没有 alpha_q、没有 exact、没有 method、没有 qalpha、没有 PNG 量化。**

它做不到的三件事：

- **动图必然被压平**：Imagick 里 `setIteratorIndex(0)`，GD 里 `imagegif()` 只写单帧。上传动图后所有子尺寸都是第一帧静图。这是功能缺失，不是画质差异。
- **CMYK 零兜底**：核心五个文件里 `cmyk` 零命中。
- **元数据反向保护**：它把 icc / icm / iptc / exif / xmp 列为 `protected_profiles`，不清反保。

所以本插件的价值在**编码参数 + 动图不毁 + 元数据策略 + 自带二进制不受宿主影响**，跟"用不用 ImageMagick"没关系。

**注意一个容易说错的事实**：ImageMagick 本身**是**暴露了 `webp:alpha-quality` 和 `webp:exact` 的，所以卖点不能写成"IM 做不到"，而应该是：① WP 核心一行都没设；② IM 把 near_lossless 和 quality 绑死，不能独立调；③ IM 处理动图是 coalesce 后重编，实测体积更大；④ IM 依赖宿主环境不可控。

### 8.5 市场先例（说明这条路线跑了十几年还有人用）

- **EWWW Image Optimizer**（100 万+ 安装）：`jpegtran / optipng / pngout / pngquant / gifsicle / cwebp`，2026 年的 changelog 仍在逐项更新工具版本。
- **spatie/image-optimizer**（PHP 事实标准）：JpegOptim / Optipng / Pngquant / SVGO / Gifsicle / cwebp / avifenc。
- **ImageOptim**（macOS，这套哲学的祖师爷）：Zopfli / PNGOUT / OxiPNG / AdvPNG / PNGCrush / JPEGOptim / Jpegtran / Guetzli / Gifsicle / SVGO / MozJPEG。

差异化空间：spatie 用的是 optipng（不是 oxipng），而且它的 AVIF 参数 `--minalpha / --maxalpha` 在 libavif 1.4.2 里已标记 Deprecated。

## 九、待办与风险清单

**高优先（净赚，不涉及取舍）**

- [x] 动画 WebP 重压：去掉 ImageMagick，改 FFmpeg libwebp_anim 一条命令（2026-10-18 完成，webpmux 逐帧重组方案作废）
- [ ] CMYK JPEG：去掉 FFmpeg + GD，改 djpeg + cjpeg（需 libjpeg-turbo ≥ 3.1.0）
- [ ] 动画 AVIF 信息读取：去掉 ffprobe，改 avifdec --info 或盒子解析
- [ ] 补进 `dwebp.exe` 与 `webpinfo.exe`
- [ ] pngquant 升级到 3.0.3
- [ ] 有损动画 WebP 加 `-exact`（gif2webp 需要；FFmpeg 路线没有这个开关，做不到）
- [ ] AVIF 带 alpha 的图改走 `-y 444`，并显式设 `--qalpha`

**中优先（涉及权衡，需要定策略）**

- [ ] 动图分"无损通道（默认开）/ 跨格式转换通道（默认关）"
- [ ] JPEG 可选有损重编码开关（cjpeg / mozjpeg）
- [ ] APNG → WebP 是否继续依赖 FFmpeg，或改 apngdis + 自合成（工程量大、风险高）

**风险登记**

- 动画 AVIF 只有第一帧的 ICC / Exif / XMP 会被保留；当前 FFmpeg 在部分 RGB 动画重压时丢 ICC，已采取"拒绝替换"策略。
- libwebp Windows 包必须选 no-wic 版，否则 PNM 通道不可用。
- oxipng 只能用 `--strip safe`，`all` 会毁掉 APNG。
- libjxl 必须 ≥ 0.12.0（大量安全修复）。
- avifenc / avifdec 喂 APNG 会静默丢帧且返回成功，任何拆帧路线都必须自己校验帧数。
